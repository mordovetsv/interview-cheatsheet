ВопросОтвет
easyЧто такое Pod?Минимальная единица деплоя — один или несколько контейнеров, разделяющих сеть и хранилище. Контейнеры в поде общаются через localhost. Под эфемерен — умер, пересоздан с новым IP.
easyЧем Deployment отличается от Pod?Pod — конкретный экземпляр. Deployment — контроллер, следит чтобы нужное число реплик Pod всегда работало. Если Pod умрёт — Deployment создаст новый. Описывает желаемое состояние, Controller Manager его реализует.
easyЧто такое Service?Стабильный сетевой адрес для набора Pod. Поды умирают и пересоздаются с новыми IP, а Service даёт постоянный DNS-адрес и балансирует трафик. Реализуется через kube-proxy.
easyТипы Service?ClusterIP — внутри кластера. NodePort — открывает порт на каждой ноде. LoadBalancer — внешний балансировщик облака. ExternalName — alias на внешний DNS. ClusterIP используется чаще всего — для межсервисного общения внутри кластера.
easyЧто хранит etcd?Всё состояние кластера: какие поды запущены, на каких нодах, какие сервисы существуют, конфиги, секреты. CP-система по CAP — при потере кворума перестаёт отвечать, не отдаёт устаревшие данные.
midЧто делает kubelet?Агент на каждой рабочей ноде. Получает от API Server описание подов, запускает контейнеры через container runtime, следит за их здоровьем и сообщает статус обратно.
midЧто делает kube-proxy?Настраивает сетевые правила (iptables/ipvs) на каждой ноде. Когда приходит запрос к Service — маршрутизирует к одному из живых Pod. CoreDNS резолвит имена в IP, kube-proxy обеспечивает маршрутизацию.
midLiveness vs Readiness probe?Liveness — жив ли контейнер? Если нет — k8s перезапускает. Readiness — готов ли принимать трафик? Если нет — убирает Pod из балансировки, не перезапускает. Startup probe — даёт время на старт медленным приложениям.
midConfigMap vs Secret?Оба хранят конфигурацию и прокидываются в Pod через переменные среды или файлы. Secret — для чувствительных данных, хранится в base64 (не encrypted по умолчанию) и имеет ограниченный доступ по RBAC.
midЧто такое Namespace?Виртуальное разделение кластера. Ресурсы в разных Namespace изолированы по имени и квотам. Обычно используют для разделения окружений (dev/staging/prod) или команд. kube-system — namespace системных компонентов k8s.
midКак работает HPA?Horizontal Pod Autoscaler — следит за метриками (CPU, memory, кастомными) и меняет количество реплик. Требует Metrics Server. Не работает корректно без правильно выставленных requests.
midRolling Update vs Recreate?Rolling — постепенно заменяет старые Pod новыми, zero-downtime. Recreate — убивает все старые, потом создаёт новые, есть даунтайм. Для stateful приложений где две версии несовместимы используют Recreate.
midPV и PVC?PV — реальное хранилище (диск, NFS). PVC — заявка Pod на хранилище нужного размера и типа. k8s матчит PVC с подходящим PV. Позволяет абстрагировать Pod от конкретного типа хранилища.
hardStatefulSet vs Deployment?Для stateful приложений (БД, Kafka). Гарантирует: стабильные имена Pod (pod-0, pod-1), порядок запуска/остановки, стабильное хранилище на каждый Pod. Deployment не даёт ни одного из этих гарантий.
hardЧто такое Ingress?HTTP/HTTPS роутер уровня L7. Позволяет направлять трафик по хосту или пути (/api → api-service). Требует Ingress Controller. Service LoadBalancer — L4, Ingress — L7.
hardЧто такое Headless Service?Service с clusterIP: None — DNS возвращает IP-адреса всех подов напрямую. StatefulSet + Headless даёт каждому поду стабильный DNS: kafka-0.kafka-headless.ns.svc.cluster.local. Брокеры Kafka находят друг друга по этим именам.
hardRBAC в k8s?Role — набор разрешений в namespace. ClusterRole — по всему кластеру. RoleBinding — привязывает Role к пользователю/ServiceAccount. ServiceAccount — identity для Pod внутри кластера.
ВопросОтвет
easyКак посмотреть логи пода?kubectl logs <pod> — текущие логи. --previous — логи упавшего контейнера (нужен при CrashLoopBackOff). -f — follow в реальном времени. --tail=100 — последние 100 строк.
easyКак зайти внутрь работающего пода?kubectl exec -it <pod> -- /bin/sh. Для distroless образов shell отсутствует — используют ephemeral debug containers: kubectl debug -it <pod> --image=busybox.
easyКак применить манифест?kubectl apply -f deployment.yaml — декларативное применение. kubectl get pods -w — наблюдать как поды поднимаются. kubectl rollout status deployment/app — дождаться завершения rolling update.
midКакие манифесты писал сам?Deployment — описание подов. Service (ClusterIP) — внутренний адрес. ConfigMap — конфиги. Secret — токены. Ingress — роутинг. HPA — автомасштабирование.
midКак настраивал liveness и readiness пробы?Readiness: httpGet: /actuator/health/readiness — Spring Boot Actuator отдаёт 200 когда приложение готово. Liveness: /actuator/health/liveness. initialDelaySeconds: 30 — даёт время на старт. Без readiness трафик пойдёт на под до готовности → 503.
midКак передавал секреты в под?Через k8s Secret: kubectl create secret generic db-secret --from-literal=password=..., в манифесте — env: valueFrom: secretKeyRef. Для шифрования at-rest нужен Vault или sealed-secrets.
midЧто делал если под не стартовал?kubectl describe pod <name> — раздел Events: ImagePullBackOff, OOMKilled, FailedScheduling. Потом kubectl logs <pod> --previous — логи до краша.
midКак выставлял ресурсы requests/limits?requests — гарантированные ресурсы. limits — максимум. Цифры из нагрузочного тестирования через kubectl top pod. CPU throttling не убивает под, OOM — убивает.
midСталкивался с CrashLoopBackOff?kubectl logs <pod> --previous — логи до краша. Частые причины: exception при старте (неверный конфиг, нет БД), OOMKilled, liveness probe убивает под раньше старта → увеличить initialDelaySeconds.
midКак обновлял без простоя? maxSurge и maxUnavailable?Rolling Update: maxSurge: 1 — сколько дополнительных подов сверх desired. maxUnavailable: 0 — нельзя убивать старые пока новый не готов. Readiness probe управляет переключением трафика.
midКак масштабировал?Вручную: kubectl scale deployment app --replicas=5. HPA: targetCPUUtilizationPercentage: 70. minReplicas: 2 — всегда минимум 2 для отказоустойчивости.
hardКак откатить деплой?kubectl rollout undo deployment/app — откат к предыдущей ревизии. --to-revision=3 — к конкретной. kubectl rollout history deployment/app — история. k8s хранит несколько предыдущих ReplicaSet для отката.
ВопросОтвет
easyTopic, Partition, Offset?Topic — именованный канал сообщений. Partition — физическое разбиение топика, единица параллелизма. Offset — порядковый номер сообщения внутри партиции, никогда не уменьшается. Committed offset — последний подтверждённый consumer-ом.
easyЧто такое Consumer Group?Несколько consumers объединённых в группу — каждая партиция назначается ровно одному consumer в группе. Разные группы читают независимо. Rebalance при изменении группы.
easyГарантии доставки?At-most-once — коммит до обработки, возможна потеря. At-least-once — после обработки, возможны дубли. Exactly-once — транзакции + идемпотентный producer.
easyBroker и KRaft?Broker — сервер Kafka, хранит партиции. Раньше метаданные кластера хранились в ZooKeeper. С Kafka 3.x — KRaft: встроенный Raft-консенсус, ZooKeeper не нужен.
midКак выбрать Partition Key?Сообщения с одним ключом всегда попадают в одну партицию — гарантируется порядок. Ключ выбирают по сущности, для которой важен порядок: orderId, userId. Без ключа — round-robin по партициям, порядок не гарантирован.
midReplication Factor и ISR?RF — сколько копий каждой партиции на разных брокерах. ISR — реплики, синхронизированные с лидером. Запись считается успешной когда подтвердили все ISR (acks=all).
midЧто такое Rebalance?Перераспределение партиций между consumers. Происходит при: добавлении/удалении consumer, падении consumer, изменении числа партиций. Во время rebalance потребление приостанавливается. Решение: CooperativeStickyAssignor.
midЧто такое DLQ?Отдельный топик куда отправляют сообщения после N неудачных retry. Без DLQ одно "ядовитое" сообщение может заблокировать всю партицию навсегда. В Spring Kafka — DeadLetterPublishingRecoverer.
midКак настроить retention?retention.ms — время хранения (дефолт 7 дней). retention.bytes — максимальный размер партиции. log.cleanup.policy=compact — compaction: хранит только последнее сообщение для каждого ключа.
midacks=0, acks=1, acks=all?0 — не ждём подтверждения, возможна потеря. 1 — только от лидера, реплики могут отстать. all — от всех ISR, максимальная надёжность.
hardКак реализовать exactly-once?Идемпотентный producer + транзакции (transactional.id). Producer атомарно пишет в несколько топиков. Consumer: isolation.level=read_committed — читает только закоммиченные.
hardЧто такое Outbox Pattern?Решает dual-write: пишем событие в таблицу outbox в той же транзакции что бизнес-данные. Debezium/CDC читает outbox и публикует в Kafka.
hardConsumer Lag?Разница между последним offset в партиции и committed offset группы. Мониторят через JMX или Micrometer + Prometheus. Высокий lag = consumer не успевает за producer.
hardСколько partitions нужно?Число partitions = максимальный желаемый параллелизм consumer. Больше partitions = больше файлов на брокере, дольше rebalance. Начать с 12–24, увеличивать по нагрузке. Уменьшить нельзя.
ВопросОтвет
easyКак объявить consumer в Spring Kafka?@KafkaListener(topics = "payment.events", groupId = "screening-group") на методе. Spring Boot автоконфигурирует ConsumerFactory по application.yml. @EnableKafka через starter включается автоматически.
easyКак отправить сообщение?KafkaTemplate: kafkaTemplate.send("topic", key, payload) — возвращает CompletableFuture. Ключ определяет партицию — всегда передавай осмысленный ключ для гарантии порядка.
easyКак проверить сообщения в топике локально?Kafka UI — браузерный интерфейс. Или kafka-console-consumer.sh --topic ... --from-beginning. В тестах — EmbeddedKafka поднимает Kafka в памяти.
midКакую задачу решал через Kafka?Получение событий о транзакциях для проверки по 115-ФЗ. REST — синхронный: платёжная система ждёт ответа комплаенса. Kafka: асинхронность, retention 7 дней, можно перечитать топик при баге в consumer-е.
midКак гарантировал порядок?Порядок гарантирован только внутри партиции. Ключ — clientId: все события по одному клиенту → одна партиция. Consumer в группе — строго один на партицию, иначе порядок теряется.
midКак настраивал продюсера?acks=all — подтверждение от всех ISR. retries=3 с retry.backoff.ms=1000. enable.idempotence=true — брокер отклоняет дубли при retry.
midКак обрабатывал ошибки в consumer-е?DefaultErrorHandler с FixedBackOff(1000, 3). После исчерпания — DeadLetterPublishingRecoverer → топик payment.events.DLT.
midКак избегал дублей?Таблица processed_events с event_id из заголовка. INSERT ... ON CONFLICT DO NOTHING — если 0 rows affected, уже обработано, пропускаем. Весь флоу в одной транзакции с бизнес-логикой.
midКак мониторили Kafka?Micrometer + Prometheus: метрика kafka.consumer.fetch.manager.records.lag.max. В Grafana — дашборд по lag. Алерт: lag > 1000 сообщений дольше 5 минут.
hardЧто делали если lag рос?kafka-consumer-groups.sh --describe — lag по партициям. Если consumer перегружен — увеличиваем инстансы (не больше числа партиций). Если медленная обработка — профилируем: N+1 в БД. Снижаем max.poll.records.
hardКак настраивал max.poll.records?Дефолт 500. При тяжёлой обработке снижали до 50–100, чтобы не превысить max.poll.interval.ms. Формула: max.poll.records ≤ max.poll.interval.ms / avg_processing_time.
hardКак минимизировали ребалансировку?CooperativeStickyAssignor — incremental rebalance. Static membership (group.instance.id) — consumer возвращается к своим партициям без rebalance при рестарте.
ВопросОтвет
easyЧем контейнер отличается от VM?VM включает полную ОС и гипервизор — тяжёлая. Контейнер разделяет ядро хоста, изолируется через namespaces и cgroups — лёгкий, стартует за секунды.
easyЧто такое Docker Image и Layer?Image — readonly шаблон из слоёв. Каждая инструкция в Dockerfile (RUN, COPY) создаёт новый слой. Слои кэшируются — если слой не изменился, пересборки нет. Union filesystem объединяет слои.
easyCMD vs ENTRYPOINT?ENTRYPOINT — основная команда, не переопределяется при запуске. CMD — аргументы по умолчанию, легко переопределяются. Лучше: ENTRYPOINT=бинарь, CMD=дефолтные аргументы. exec форма ["java","-jar","app.jar"] — PID 1 напрямую.
easyCOPY vs ADD?COPY — просто копирует файлы. ADD — умеет распаковывать архивы и скачивать по URL. В большинстве случаев используй COPY — поведение предсказуемее. ADD только когда нужна распаковка.
easyЧто такое Docker Volume?Персистентное хранилище вне контейнера. Данные в контейнере эфемерны. Volume хранится на хосте (/var/lib/docker/volumes) и переживает пересоздание. Bind mount — альтернатива: монтируешь конкретную директорию хоста.
midКак уменьшить размер образа?Multi-stage build — только артефакт в slim-образ. Alpine/distroless. Объединяй RUN через &&. .dockerignore — не копируй лишнее.
midЧто такое Multi-stage build?Несколько FROM в Dockerfile. Stage 1 — компиляция (JDK, Maven). Stage 2 — только JRE + jar. Для Java: с ~600 МБ до ~150 МБ.
midКак работает Docker сеть?По умолчанию контейнеры в одной bridge-сети общаются по имени контейнера. host — контейнер использует сеть хоста. В Compose сервисы автоматически в одной сети.
midЗачем нужен .dockerignore?Исключает файлы из build context. Без него target/, .git попадут в контекст → медленная сборка, большой образ.
midARG vs ENV?ARG — только на этапе сборки, не попадает в финальный образ. ENV — переменная среды в runtime. Секреты нельзя в ARG — остаются в истории слоёв. Передавай секреты через env при запуске.
hardКак работают namespaces и cgroups?Namespaces — изолируют процессы: каждый контейнер видит своё дерево процессов, сеть, файловую систему. cgroups — ограничивают ресурсы. Docker — обёртка над этими механизмами ядра Linux.
hardЧем distroless лучше alpine?Distroless — нет shell, пакетного менеджера, утилит. Alpine добавляет busybox. Distroless: меньше CVE, меньше поверхность атаки. Alpine: есть shell для отладки. В продакшене — distroless.
hardКак ограничить ресурсы?docker run --memory=512m --cpus=1.5. Без ограничений один контейнер может съесть всю память хоста → OOM killer убьёт другие процессы. В k8s: resources.limits и resources.requests.

easyКак собрать и запустить образ?docker build -t myapp:1.0 . — сборка с тегом. docker run -p 8080:8080 myapp:1.0 — запуск с пробросом порта. -d — фоновый режим. docker ps — список запущенных.
easyКак посмотреть логи и остановить контейнер?docker logs <container>. -f — follow. docker stop — graceful shutdown (SIGTERM). docker kill — немедленно (SIGKILL). docker rm — удалить.
easyКак чистил дисковое пространство?docker system prune — удаляет остановленные контейнеры, dangling образы, неиспользуемые сети. -a — также все образы без тега. docker image prune — только образы.
midКак выглядел твой Dockerfile?Stage 1: FROM maven:3.9-eclipse-temurin-21 AS build → COPY pom.xml . → RUN mvn dependency:go-offline → COPY src ./src → RUN mvn package -DskipTests. Stage 2: FROM eclipse-temurin:21-jre-alpine → COPY --from=build target/*.jar app.jar → ENTRYPOINT ["java","-jar","/app.jar"].
midПочему pom.xml копируется отдельно?Docker кэширует слой пока не изменился его входной контент. pom.xml меняется редко → слой с mvn dependency:go-offline кэшируется. При изменении только кода — зависимости не скачиваются заново, сборка намного быстрее.
midЗапускал ли контейнер от root?Нет. RUN addgroup -S app && adduser -S app -G app, затем USER app. Системный пользователь без shell и домашней директории. При эскалации привилегий через уязвимость — атакующий получает app, не root.
midКак передавал переменные и секреты?docker run -e DB_PASSWORD=... или env_file: .env в Compose. Секреты не хардкодить в ENV в Dockerfile — остаются в истории слоёв. В k8s: через Secret как переменная среды.
midКак отлаживал контейнер, который не стартовал?docker logs <container> — stacktrace. docker inspect <container> — env, volumes, сеть. Если не запускается вообще — docker run --entrypoint sh image — зайти без основного процесса.
midИспользовал ли docker-compose?Для локальной разработки — поднять PostgreSQL + Redis + Kafka одной командой docker compose up -d. В тестах — Testcontainers: контейнеры стартуют и останавливаются сами в рамках теста.
midКак передавал JVM-флаги?Через JAVA_TOOL_OPTIONS: -e JAVA_TOOL_OPTIONS="-Xmx512m -Xms256m". Гибче чем зашивать в Dockerfile — переопределяется при запуске без пересборки.
hardКак настраивал health check?HEALTHCHECK --interval=30s --timeout=3s CMD curl -f http://localhost:8080/actuator/health || exit 1. В k8s используют readiness probe вместо Docker healthcheck — более тонкий контроль (liveness отдельно от readiness).
ВопросОтвет
easyТипы JOIN?INNER — только совпадающие строки. LEFT — все из левой + совпадения справа (NULL если нет). RIGHT — наоборот. FULL — все из обеих. CROSS — декартово произведение.
easyWHERE vs HAVING?WHERE фильтрует строки до группировки, HAVING — группы после GROUP BY. В HAVING можно использовать агрегатные функции, в WHERE — нет. Порядок выполнения: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
easyЧто такое индекс?Структура данных (обычно B-tree) для ускорения поиска. Ускоряет SELECT, замедляет INSERT/UPDATE/DELETE — при изменении данных индекс тоже обновляется. Занимает место на диске.
easyPRIMARY KEY vs UNIQUE?PK — уникальный идентификатор строки, NOT NULL + UNIQUE, один на таблицу, автоматически индексируется. UNIQUE — ограничение уникальности, допускает NULL, может быть несколько на таблицу.
midЧто такое ACID?Atomicity — всё или ничего. Consistency — БД переходит из одного валидного состояния в другое. Isolation — параллельные транзакции не мешают друг другу. Durability — после commit данные не потеряются даже при сбое (через WAL).
midУровни изоляции транзакций?READ UNCOMMITTED — видны незакоммиченные изменения (dirty read). READ COMMITTED — дефолт в PostgreSQL, возможен non-repeatable read. REPEATABLE READ — возможен phantom read. SERIALIZABLE — полная изоляция.
midСоставной индекс — порядок колонок важен?Да, критично. Индекс (a, b, c) работает для запросов по a, a+b, a+b+c, но НЕ для запроса только по b или c. Это leftmost prefix rule. Самую селективную колонку — первой.
midЧто такое N+1 проблема?Один запрос получает N записей, затем для каждой делается отдельный запрос → N+1 запросов вместо одного. Типично в ORM при ленивой загрузке связей. Решение: JOIN FETCH, @EntityGraph, @BatchSize.
midПодзапрос vs JOIN?JOIN обычно быстрее — оптимизатор может выбрать лучшую стратегию соединения. Коррелированный подзапрос выполняется для каждой строки — особенно медленно. Но EXISTS иногда быстрее JOIN когда нужна только проверка наличия.
midОконные функции?Вычисляют значение по «окну» строк без схлопывания: ROW_NUMBER(), RANK(), LAG(), SUM() OVER (PARTITION BY ...). В отличие от GROUP BY сохраняют все строки. Полезны для пагинации, рейтингов, скользящих сумм.
midCTE — зачем?WITH cte AS (...) — именованный подзапрос. Улучшает читаемость сложных запросов, позволяет рекурсию для обхода иерархий. В PostgreSQL 12+ CTE инлайнится оптимизатором, раньше был барьером оптимизации.
hardТипы индексов в PostgreSQL?B-tree — дефолт, для =, <, >, сортировки. GIN — массивы, jsonb, полнотекстовый поиск. BRIN — огромные таблицы с естественным порядком. Частичный — WHERE is_active = true.
hardЧто такое MVCC в PostgreSQL?Multi-Version Concurrency Control — каждая транзакция видит свой снимок данных. При UPDATE создаётся новая версия строки, старая помечается как мёртвая. Читатели не блокируют писателей. Обратная сторона — нужен VACUUM для очистки мёртвых версий.
hardDeadlock — что это и как избежать?Взаимная блокировка: A ждёт ресурс B, B ждёт ресурс A. PostgreSQL обнаруживает и откатывает одну транзакцию с ошибкой. Профилактика: всегда захватывать ресурсы в одном порядке, минимизировать длительность транзакций, использовать SELECT ... FOR UPDATE осознанно.
hardПессимистичная vs оптимистичная блокировка?Пессимистичная — SELECT ... FOR UPDATE, блокирует строки, другие ждут. Для высококонкурентных критичных операций. Оптимистичная — колонка version, при конфликте UPDATE не проходит → исключение → retry. Меньше блокировок, лучше масштабируется.

easyКак посмотреть план запроса?EXPLAIN ANALYZE SELECT ... — реально выполняет запрос и показывает фактическое время. EXPLAIN без ANALYZE — только оценка планировщика. Смотрю: Seq Scan на больших таблицах, Nested Loop, расхождение estimated vs actual rows.
easyКак посмотреть существующие индексы?\d table_name в psql — покажет структуру и индексы. Или SELECT * FROM pg_indexes WHERE tablename = 'transactions';. Размер индексов: SELECT pg_size_pretty(pg_relation_size('idx_name'));
easyКак найти медленные запросы?pg_stat_statements: SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;. В Spring — spring.jpa.show-sql=true + логирование времени выполнения.
midКак оптимизировал запросы к транзакциям?Через EXPLAIN ANALYZE увидел Seq Scan по 10+ млн строк. Добавил составной индекс (client_id, transaction_date) — порядок важен, client_id в WHERE, дата в диапазоне. Переписал коррелированные подзапросы на JOIN с подзапросом-агрегатом. Итог: с 5-7 сек до 0.5-1 сек.
midКак понять что индекс не используется?В EXPLAIN ANALYZE видно Seq Scan вместо Index Scan. Причины: низкая селективность, функция над колонкой в WHERE (WHERE UPPER(name) = ... — нужен functional index), несоответствие типов, устаревшая статистика → ANALYZE table;
midКак писал миграции Liquibase?Один changeset = одно логическое изменение, никогда не редактировать применённый changeset (checksum сломается). Всегда <rollback>. <preConditions onFail="MARK_RAN"> — идемпотентность. Для больших таблиц — CREATE INDEX CONCURRENTLY чтобы не блокировать.
midКак делал пагинацию по большой таблице?OFFSET плох на больших смещениях — БД всё равно читает все пропущенные строки. Лучше keyset pagination: WHERE id > :lastId ORDER BY id LIMIT 50. Или оконная функция ROW_NUMBER() когда нужна сложная сортировка.
midКак искал неиспользуемые индексы?SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0; — индексы которые ни разу не использовались. Каждый лишний индекс замедляет запись и занимает место. Перед удалением проверить что статистика собиралась достаточно долго.
midКак понять что таблица раздулась?Bloat из-за MVCC: pg_stat_user_tables → n_dead_tup. Если мёртвых строк много относительно живых — autovacuum не справляется, надо тюнить его агрессивность или делать VACUUM FULL в окно.
hardКак добавлял индекс на большую таблицу в проде?CREATE INDEX CONCURRENTLY — не берёт эксклюзивную блокировку, таблица остаётся доступной для записи. Медленнее и может упасть, оставив невалидный индекс. В Liquibase — через <sql> с runInTransaction="false".
hardКак искал причину deadlock?Логи PostgreSQL показывают обе транзакции и какие блокировки конфликтовали (log_lock_waits = on). pg_locks + pg_stat_activity — что блокируется прямо сейчас. Фикс: упорядочить захват ресурсов, сократить транзакции, иногда сменить уровень изоляции.
hardКак тестировал запросы к БД?Testcontainers с реальным PostgreSQL — H2 врёт про поведение (другой SQL-диалект, нет оконных функций в некоторых версиях). Database Rider — датасеты в YAML через @DataSet. @Sql в Spring для простых случаев.

easyЧто такое IoC и DI?IoC — объект не создаёт свои зависимости сам, контейнер их предоставляет. DI — конкретная реализация: через конструктор (рекомендуется), сеттер или поле. Плюсы: тестируемость (легко подменить моком), слабая связанность.
easy@Component, @Service, @Repository — разница?Функционально почти идентичны — все создают бин. Семантически: @Service — бизнес-логика, @Repository — доступ к данным (плюс трансляция исключений БД), @Controller — веб-слой.
easyScope бинов?singleton — дефолт, один экземпляр на контейнер. prototype — новый при каждом получении. request/session — для веб-приложений. Важно: singleton должен быть stateless, иначе гонки между потоками.
midКак работает @Transactional?Spring создаёт прокси вокруг бина: открывает транзакцию до метода, коммитит после, откатывает при RuntimeException. Вызов изнутри класса не работает — прокси не задействован. По умолчанию откат только на unchecked исключениях.
midPropagation транзакций?REQUIRED — дефолт, присоединяется к существующей или создаёт новую. REQUIRES_NEW — всегда новая, внешняя приостанавливается. NESTED — вложенная через savepoint. SUPPORTS — работает с транзакцией если есть, без неё если нет. MANDATORY — требует существующую, иначе исключение.
midЧто такое автоконфигурация?Spring Boot сканирует classpath и настраивает бины автоматически. Работает через @ConditionalOnClass, @ConditionalOnMissingBean и файл AutoConfiguration.imports. Свой бин переопределяет автоконфигурационный.
midЧто такое Spring Boot Starter?Модуль с набором зависимостей + автоконфигурация. Свой стартер: @AutoConfiguration класс + @ConfigurationProperties + регистрация в AutoConfiguration.imports. Позволяет переиспользовать инфраструктурный код между сервисами команды.
midAOP в Spring?Вынос сквозной функциональности в аспекты. Pointcut — где применять, Advice — что делать. На этом построены @Transactional, @Cacheable, @Async, Spring Security.
hardЖизненный цикл бина?Инстанцирование → внедрение зависимостей → BeanNameAware/BeanFactoryAware → BeanPostProcessor.before → @PostConstruct → afterPropertiesSet → BeanPostProcessor.after → готов → @PreDestroy → destroy.
hardКак решается циклическая зависимость?При конструкторной инъекции — BeanCurrentlyInCreationException, Spring не может разорвать цикл. Варианты: @Lazy на одной из зависимостей, инъекция через сеттер, или (лучше) рефакторинг — цикл обычно признак неправильного разделения ответственности. В Spring Boot 2.6+ циклы запрещены по умолчанию.
hard@Async — как работает?Метод выполняется в отдельном потоке через прокси. Требует @EnableAsync. Дефолтный executor опасен — создаёт новый поток на каждый вызов. Нужно определить свой ThreadPoolTaskExecutor с bounded queue. Как и @Transactional — не работает при self-invocation.
hardЧто такое ApplicationContext vs BeanFactory?BeanFactory — базовый контейнер, ленивая инициализация. ApplicationContext — расширяет его: события, интернационализация, AOP, автоматическая регистрация BeanPostProcessor, eager-инициализация singleton'ов при старте.
ВопросОтвет
easyКак обрабатывал ошибки в REST API?@RestControllerAdvice + @ExceptionHandler на каждый тип исключения. Возвращаю единый формат ошибки (ProblemDetail в Spring 6). Не отдаю stacktrace наружу — только код ошибки и сообщение.
easyКак валидировал входные данные?Bean Validation: @NotNull, @Size, @Email на полях DTO + @Valid в контроллере. Кастомная валидация — свой ConstraintValidator. Ошибки ловлю в @ExceptionHandler(MethodArgumentNotValidException.class).
easyКак конфигурировал приложение под разные окружения?Профили: application-dev.yml, application-prod.yml, активация через SPRING_PROFILES_ACTIVE. @Profile("dev") на бинах. Секреты — не в yml, а через переменные окружения или k8s Secret.
midКак писал свой Spring Boot стартер?@AutoConfiguration класс с @Bean методами, @ConditionalOnMissingBean чтобы пользователь мог переопределить, @ConfigurationProperties для настроек из yml. Регистрация в META-INF/spring/...AutoConfiguration.imports. Подключил зависимость — бины настроились сами.
midГде ставил @Transactional и почему?На методах сервисного слоя — там границы бизнес-операции. Не на репозиториях (Spring Data и так транзакционен), не на контроллерах (слишком широкая граница, транзакция висит пока идёт сериализация). @Transactional(readOnly = true) на чтении — Hibernate пропускает dirty checking.
midКак настраивал пул потоков для @Async?Свой ThreadPoolTaskExecutor: corePoolSize, maxPoolSize, bounded queue и CallerRunsPolicy для backpressure. Дефолтный SimpleAsyncTaskExecutor создаёт новый поток на каждый вызов — в проде это путь к OOM.
midКак тестировал сервисы?Юнит-тесты: чистый JUnit + Mockito, без контекста Spring — быстро. Интеграционные: @SpringBootTest + Testcontainers. Контроллеры: @WebMvcTest + MockMvc — только веб-слой, быстро.
midКак логировал в приложении?SLF4J + Logback, @Slf4j от Lombok. Структурированные логи в JSON для парсинга в ELK. MDC с traceId — сквозная трассировка запроса через сервисы. Никогда не логирую персональные данные и секреты.
hardКак реализовал retry для внешних вызовов?Resilience4j: @Retry(name="fns") с exponential-backoff-multiplier: 2 — паузы 1с, 2с, 4с. Плюс @CircuitBreaker с fallback — если сервис стабильно падает, перестаём его дёргать. Ретраить только идемпотентные операции и transient ошибки (5xx, таймаут), не 4xx.
hardКак параллелил внешние вызовы?CompletableFuture.allOf(...) с кастомным executor. Дефолтный ForkJoinPool.commonPool не подходит — он CPU-bound и общий на приложение. Взял ThreadPoolExecutor с bounded queue. В Java 21 для IO-bound логичнее виртуальные треды.
hardКак снимал метрики приложения?Spring Boot Actuator + Micrometer → Prometheus → Grafana. Кастомные метрики через MeterRegistry: Counter, Timer, Gauge. Смотрел: latency перцентили (p95, p99), error rate, hikaricp.connections.pending, GC паузы.
ВопросОтвет
easyJPA vs Hibernate vs Spring Data JPA?JPA — спецификация (интерфейсы и аннотации). Hibernate — самая популярная реализация. Spring Data JPA — надстройка, генерирует реализации репозиториев по именам методов (findByEmail → SQL).
easyСостояния сущности?Transient — новый объект, не связан с контекстом. Managed — в persistence context, изменения автоматически попадут в БД. Detached — был managed, контекст закрыт. Removed — помечен на удаление.
easyLAZY vs EAGER загрузка?LAZY — загружается при первом обращении (прокси). EAGER — сразу. Дефолт: @ManyToOne/@OneToOne — EAGER, @OneToMany/@ManyToMany — LAZY. Практика: везде ставить LAZY и грузить явно через JOIN FETCH.
midCascade типы?PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL. Осторожно с ALL — особенно REMOVE на @ManyToMany. orphanRemoval удаляет «осиротевшие» сущности при удалении из коллекции.
midJPQL vs Native Query?JPQL — работает с сущностями (SELECT u FROM User u), портируем между БД, типобезопасен. Native — обычный SQL, нужен для специфичных функций БД, оконных функций, сложных CTE. Возвращает Object[] или маппится на DTO через @SqlResultSetMapping.
midСтратегии генерации id?IDENTITY — автоинкремент БД, но ломает batch insert. SEQUENCE — последовательность БД, поддерживает батчи, можно настроить allocationSize. TABLE — отдельная таблица, медленно. Для PostgreSQL рекомендуется SEQUENCE.
hardmerge vs persist?persist — для новых (transient) сущностей, делает managed. merge — для detached: копирует состояние в managed-копию и возвращает новый объект, оригинал остаётся detached. save() в Spring Data выбирает между ними по наличию id.
easyЧто такое EntityManager?Центральный интерфейс JPA: persist, merge, remove, find, createQuery. Управляет persistence context. В Spring внедряется через @PersistenceContext, но обычно работают через Spring Data репозитории.
easy@Entity — требования к классу?Обязателен @Id, конструктор без аргументов (public или protected), класс не final, поля не final. @Table — если имя таблицы отличается от имени класса.
mid@Embeddable и @ElementCollection?@Embeddable — класс-компонент без своего id, его поля становятся колонками родительской таблицы (например Address внутри User). @ElementCollection — коллекция value-типов в отдельной таблице, но без самостоятельного жизненного цикла.
midСтратегии наследования?SINGLE_TABLE — дефолт, одна таблица с колонкой-дискриминатором, быстро, но колонки подклассов nullable. JOINED — таблица на класс, нормализовано, но JOIN на каждый запрос. TABLE_PER_CLASS — полная таблица на класс, UNION при полиморфных запросах.
midmappedBy — владелец связи?Владеет связью та сторона, где @JoinColumn — она пишет FK. Обратная сторона помечается mappedBy = "поле". Классическая ошибка: изменить только обратную сторону — в БД ничего не поменяется.
hardCriteria API — когда нужен?Динамические запросы, где условия зависят от рантайма (фильтры в UI). Типобезопасен — опечатка в имени поля ловится компилятором, в отличие от JPQL-строки. Многословен, поэтому в Spring чаще используют Specification или QueryDSL.
hardОптимистичная блокировка в JPA?Поле с @Version (int или timestamp). При UPDATE Hibernate добавляет WHERE version = :old и увеличивает версию. Если строк обновлено 0 — кто-то изменил раньше → OptimisticLockException → обработка на уровне приложения (retry или сообщение пользователю).

easyКак писал запросы в репозитории?Простые — по имени метода: findByClientIdAndStatus(...), Spring Data сгенерирует SQL. Сложнее — @Query с JPQL. Совсем сложные (оконные функции, CTE) — @Query(nativeQuery = true). Динамические условия — Specification или QueryDSL.
easyКак видел какой SQL генерируется?spring.jpa.show-sql=true — простой вывод. Лучше: logging.level.org.hibernate.SQL=DEBUG + org.hibernate.orm.jdbc.bind=TRACE — покажет и параметры. hibernate.format_sql=true — читаемое форматирование.
easyКак маппил связь many-to-many?Если связь «чистая» (только два id) — @ManyToMany с @JoinTable. Если в связующей таблице есть свои поля (дата, статус) — отдельная сущность с двумя @ManyToOne. Для простых value-типов (список строк) — @ElementCollection.
midКак возвращал данные наружу — сущность или DTO?Всегда DTO. Сущность наружу — это LazyInitializationException, утечка схемы БД в API и риск случайной модификации managed-объекта. Маппинг — MapStruct или руками в сервисе внутри транзакции. Проекции — когда нужны 2-3 поля.
midКак делал массовые обновления?Не через загрузку сущностей в память — это тысячи UPDATE. Использовал @Modifying @Query("UPDATE ...") — один SQL. Важно: такой запрос обходит persistence context, поэтому clearAutomatically = true.
midКак маппил enum?Только @Enumerated(EnumType.STRING). Дефолтный ORDINAL хранит порядковый номер — добавил константу в середину, и старые данные поехали. STRING занимает больше места, но переживает рефакторинг enum.
midКак настраивал двунаправленную связь?Владеющая сторона — с @JoinColumn, обратная — с mappedBy. Обязательно helper-метод, который обновляет обе стороны — иначе объект в памяти и запись в БД разойдутся.
midКак ограничивал выборку полей?Проекции Spring Data: интерфейс с геттерами нужных полей, или DTO с конструктором. Hibernate выберет только эти колонки. Полезно для списков, где нужны 2-3 поля из широкой таблицы.
hardЧто делал при OptimisticLockException?Ловил и делал retry с перечитыванием актуальных данных (обычно 2-3 попытки). Если конфликт пользовательский — возвращал 409 Conflict с сообщением «данные изменились, обновите страницу». Бездумный retry в цикле опасен — при постоянном конфликте будет вечный цикл.
hardКак тестировал JPA-слой?@DataJpaTest + Testcontainers с реальным PostgreSQL. H2 обманывает — другой диалект, другое поведение с типами и функциями. Тестовые данные — Database Rider через @DataSet.
hardКак понимал что транзакция не откатывается?Spring откатывает только на RuntimeException. Checked-исключения по умолчанию НЕ откатывают — нужен @Transactional(rollbackFor = Exception.class). Вторая типичная причина — вызов метода изнутри того же класса: прокси не срабатывает, транзакции просто нет.
ВопросОтвет
easyЧто такое JDBC?Стандартный API Java для работы с БД. Спецификация интерфейсов, которые реализует драйвер конкретной БД. Цепочка: DataSource → Connection → Statement → ResultSet.
easyStatement vs PreparedStatement?Statement — SQL строкой, уязвим к инъекциям, план не кэшируется. PreparedStatement — параметры через ?, БД кэширует план выполнения. CallableStatement — для хранимых процедур.
easyЧто такое ResultSet?Курсор по результату запроса. next() двигает курсор, getString(1)/getInt("id") читают колонку. По умолчанию forward-only и read-only. Обязательно закрывать — иначе утечка ресурсов.
easyDataSource vs DriverManager?DriverManager — устаревший, создаёт новое соединение каждый раз. DataSource — современный стандарт, поддерживает пулинг и распределённые транзакции. В Spring всегда DataSource.
midЧто такое Connection Pool и зачем?Пул готовых соединений — создание соединения дорого (TCP handshake + аутентификация + ресурсы на сервере БД). Приложение берёт из пула и возвращает. HikariCP — дефолт в Spring Boot.
midКак выбрать размер пула?Не «чем больше тем лучше» — избыток соединений вредит: контекстные переключения, конкуренция за ресурсы БД. Эмпирика от HikariCP: (ядра × 2) + число дисков. Ограничение сверху — max_connections БД, делённый на число инстансов.
midКак работают транзакции в JDBC?По умолчанию autocommit = true. Для явной транзакции: conn.setAutoCommit(false) → запросы → conn.commit() или conn.rollback(). Savepoint — частичный откат.
midЧто такое batch в JDBC?addBatch() накапливает запросы, executeBatch() отправляет пачкой. Резко снижает число round-trip к БД. Оптимальный размер 500–1000. Для PostgreSQL нужен reWriteBatchedInserts=true в URL.
midКак JDBC защищает от SQL-инъекций?Только PreparedStatement с параметрами через ? — драйвер отправляет SQL и параметры отдельно, БД не интерпретирует значения как код. Конкатенация строк в Statement — прямая уязвимость, даже с экранированием.
hardЧто такое fetch size?Сколько строк драйвер забирает за раз. PostgreSQL-драйвер по умолчанию грузит весь результат в память — на больших выборках OOM. Решение: setFetchSize(1000) + setAutoCommit(false) — включает серверный курсор.
hardЧто такое утечка соединений?Соединение взято из пула и не возвращено (не закрыт Connection). Пул исчерпывается, новые запросы висят до connectionTimeout. Решение: try-with-resources, а в HikariCP — leakDetectionThreshold для диагностики.
hardЧто такое JdbcTemplate?Spring-обёртка над JDBC: убирает boilerplate (открытие/закрытие, try-catch), транслирует SQLException в DataAccessException. query() + RowMapper для маппинга. Полезен когда ORM избыточен.

easyКак правильно закрывать ресурсы?try (Connection c = ds.getConnection(); PreparedStatement ps = c.prepareStatement(sql)) { ... } — try-with-resources закроет всё в обратном порядке даже при исключении. В Spring через JdbcTemplate это делается само.
easyКак настроен DataSource в Spring Boot?В application.yml: spring.datasource.url/username/password. Spring Boot сам создаёт HikariDataSource. Настройки пула — под spring.datasource.hikari.*.
easyКак выполнить простой запрос через JdbcTemplate?jdbcTemplate.query(sql, rowMapper, params) — список. queryForObject(sql, Long.class, id) — одно значение. update(sql, params) — INSERT/UPDATE/DELETE, вернёт число затронутых строк. Параметры всегда через ?, не конкатенацией.
midКак настраивал HikariCP?maximum-pool-size — не больше чем БД выдержит (max_connections / число инстансов). connection-timeout: 30s, idle-timeout: 10min, max-lifetime — меньше таймаута БД. leak-detection-threshold: 60000 — ловит утечки.
midКак мониторил пул соединений?Micrometer экспортирует метрики HikariCP автоматически: hikaricp.connections.active, .idle, .pending. Если pending стабильно > 0 — пул мал или есть утечка. .timeout — сколько раз не дождались.
midКак делал bulk insert?JDBC batch: addBatch() в цикле + executeBatch() каждые 500–1000 записей. Для PostgreSQL обязательно reWriteBatchedInserts=true в JDBC URL — драйвер соберёт из N отдельных INSERT один многострочный. Для очень больших объёмов — COPY.
midКак ловил утечку соединений?leak-detection-threshold в HikariCP — логирует stacktrace места где соединение взяли и не вернули дольше N мс. Плюс мониторинг hikaricp.connections.active — если растёт и не падает, соединения не возвращаются. Первый подозреваемый — ручная работа с Connection без try-with-resources.
midКогда использовал JdbcTemplate вместо JPA?Когда ORM мешает: сложная аналитика с оконными функциями и CTE, массовые операции, отчёты с произвольной структурой результата. JPA хорош для CRUD над графом объектов, JdbcTemplate — когда нужен полный контроль над SQL и маппинг в плоский DTO.
hardКак читал большую выборку без OOM?setFetchSize(1000) + setAutoCommit(false) — включает серверный курсор в PostgreSQL, драйвер тянет порциями. Без этого весь результат грузится в память клиента. В Spring Data — Stream<T> из репозитория с @QueryHints(fetchSize) внутри транзакции.
hardКак обрабатывал специфичные ошибки БД?Spring транслирует SQLException в иерархию DataAccessException: DuplicateKeyException (unique violation), DataIntegrityViolationException (FK), DeadlockLoserDataAccessException. Это позволяет не парсить SQLState руками.
hardКак тестировал JDBC-код?Testcontainers с реальным PostgreSQL — H2 имеет другой диалект и молча проглатывает то, что упадёт в проде. @JdbcTest в Spring — поднимает только JDBC-слой без полного контекста, быстрее.
ВопросОтвет
easyHibernate — это что относительно JPA?Самая популярная реализация спецификации JPA. Умеет больше чем требует стандарт: @BatchSize, @Formula, @Filter, нативный Session API, статистика.
easyЧто такое Persistence Context?Кэш первого уровня, всегда включён, живёт в рамках транзакции/сессии. Повторный findById с тем же id не идёт в БД. Гарантирует что одна строка БД = один объект в памяти внутри транзакции (identity guarantee).
easyЧто такое dirty checking?При загрузке Hibernate делает снимок сущности. При flush сравнивает текущее состояние со снимком и сам генерирует UPDATE. Поэтому не нужно вызывать save() для managed-сущности — достаточно изменить поле внутри транзакции.
midКак работает LAZY-прокси?Hibernate генерирует подкласс-прокси (через ByteBuddy). При первом обращении к любому полю кроме id — идёт в БД. Отсюда особенность: getId() на прокси не вызывает запрос, а getName() вызывает.
midЧто такое N+1 и как лечить?Один запрос вернул N сущностей, обращение к LAZY-связи каждой даёт ещё N запросов. Лечение: JOIN FETCH в JPQL, @EntityGraph, @BatchSize — загрузка пачками через IN.
midЧто такое LazyInitializationException?Обращение к LAZY-связи после закрытия сессии — типично при возврате сущности из транзакционного сервиса в контроллер. Правильное решение — возвращать DTO. Неправильное — open-in-view: true, оно лишь маскирует проблему.
midРежимы flush?AUTO (дефолт) — перед commit и перед запросом, который может затронуть изменённые сущности. COMMIT — только перед коммитом. MANUAL — только явный flush(). @Transactional(readOnly = true) ставит режим, при котором dirty checking пропускается — экономия на чтении.
hardКэш второго уровня?Общий кэш на SessionFactory, живёт между транзакциями. Не включён по умолчанию, реализации: Ehcache, Hazelcast, Infinispan. Подходит для редко меняющихся справочников. Опасен если данные меняются мимо Hibernate.
hardПочему IDENTITY ломает батчи?При IDENTITY Hibernate обязан выполнить INSERT немедленно, чтобы получить сгенерированный id — накопить батч невозможно. SEQUENCE с allocationSize позволяет получить блок id заранее и собрать батч.
hardЧто делает ddl-auto?none / validate — единственно допустимые в проде (схемой управляет Liquibase/Flyway). update — опасен: не удаляет колонки, не умеет переименования. create-drop — только для тестов.
hardЧем get() отличается от load()?Нативный Hibernate API: get() сразу идёт в БД и вернёт null если нет. load() вернёт прокси без запроса, исключение прилетит позже. JPA-аналоги: find() и getReference().
hardЗачем equals/hashCode у сущности?Проблема: до persist id равен null, после — заполнен. Если hashCode считается по id, сущность «теряется» в HashSet после сохранения. Решение — business key, либо константный hashCode и equals по id.

easyКак смотрел какой SQL генерируется?logging.level.org.hibernate.SQL=DEBUG — сами запросы, org.hibernate.orm.jdbc.bind=TRACE — значения параметров. hibernate.format_sql=true — читаемый вид. spring.jpa.show-sql проще, но без параметров и без привязки к логгеру.
easyКак считал число запросов в тесте?generate_statistics + SessionFactory.getStatistics().getQueryExecutionCount(). Или библиотеки вроде datasource-proxy — позволяют делать ассерт «этот эндпоинт должен делать ровно 2 запроса» и ловить N+1 регрессией.
easyЧто ставил в ddl-auto?validate — Hibernate проверяет соответствие сущностей схеме и падает при расхождении. Схемой управляет Liquibase. update никогда в проде: не удаляет колонки, не умеет переименования, при параллельном старте нескольких инстансов может сломать схему.
midКак ловил и чинил N+1?Включал лог SQL и считал запросы на один вызов API. Чинил через JOIN FETCH или @EntityGraph. Для коллекций в списке — @BatchSize(size = 25). В тесты добавлял ассерт на число SQL-запросов, чтобы регрессия не прошла незамеченной.
midЗачем open-in-view: false?По умолчанию true — сессия держится до конца HTTP-запроса. Маскирует LazyInitializationException, но удерживает соединение из пула дольше нужного и провоцирует скрытые N+1 в слое представления.
midКак настраивал batch insert?hibernate.jdbc.batch_size: 50, order_inserts: true, order_updates: true. Обязательно SEQUENCE вместо IDENTITY — иначе батчи не работают. Каждые N записей — flush() + clear(), иначе persistence context растёт и съедает память.
midКак делал массовые обновления?Не загружая сущности — это тысячи UPDATE и раздутый контекст. Использовал @Modifying @Query("UPDATE ...") — один SQL. Важно: такой запрос обходит persistence context, поэтому clearAutomatically = true.
midКак понял что сущность не сохраняется?Частые причины: нет активной транзакции (метод не @Transactional или self-invocation); работа с detached-объектом без merge; merge вызван, но результат проигнорирован — он возвращает новый managed-объект, оригинал остаётся detached.
hardКак чинил LazyInitializationException?Правильно: маппить в DTO внутри транзакции, наружу отдавать DTO. Если нужна связь — JOIN FETCH или @EntityGraph при загрузке. Неправильно, но встречается: open-in-view: true или @Transactional на контроллере — оба расширяют границу транзакции туда, где ей не место.
hardКак писал equals/hashCode для сущностей?Не по всем полям и не через Lombok @Data — он включает id и коллекции, что ломает поведение в Set и вызывает подгрузку LAZY-связей. Практика: equals по id с проверкой на null, hashCode — константа от класса, либо business key если он есть.
hardКак тестировал Hibernate-слой?@DataJpaTest + Testcontainers с реальным PostgreSQL — H2 имеет другой диалект и пропускает ошибки, которые вылезут в проде. @DataJpaTest по умолчанию откатывает транзакцию — нужен явный flush() чтобы проверить констрейнты.
